## 快速开始

### 安装

```bash
# 全局安装（稳定版）
npm install -g @pennixrv/trellis@latest

# 进入你的项目目录
cd your-project
```

<Note>**系统要求**：Mac、Linux、Windows 全部支持。需要 Node.js 18+ 和 Python 3.9+。</Note>

`trellis init` 会自动检测已安装的平台，也可以用 flag 显式指定。每一个平台都需要最少 init 一次。随意组合：

```bash
# 交互式：检测已安装的平台并询问要配置哪些
trellis init -u your-name

# 显式：配置一个或多个平台
trellis init -u your-name --claude
trellis init -u your-name --claude --cursor --opencode
trellis init -u your-name --codex --gemini
trellis init -u your-name --pi
```

`your-name` 会成为你的开发者身份，在 `.trellis/workspace/your-name/` 创建个人工作区。

支持的 flag：`--claude`、`--cursor`、`--opencode`、`--codex`、`--kiro`、`--gemini`、`--qoder`、`--codebuddy`、`--copilot`、`--droid`、`--pi`、`--antigravity`、`--devin`（别名：`--windsurf`，已废弃）、`--kilo`、`--reasonix`、`--zcode`、`--omp`、`--trae`、`--grok`、`--kimi`、`--snow`、`--dsh`。

除了这 22 个已配置平台，任何读取 `.agents/skills/` 规范的 AI 编码 agent（Amp、Cline、Deep Agents、Firebender、Warp 等）也能直接消费 Trellis：Codex 的 skill 就写在这个目录下，这些文件能被该生态的其他 agent 直接读取。

### 升级

升级是**两步**——CLI 和项目里的 `.trellis/` 模板是分开版本化的：

```bash
trellis upgrade   # 1. 升级全局 CLI package
trellis update    # 2. 在每个项目里：把 .trellis/ 和平台文件同步到新 CLI
```

<Warning>
  如果 `trellis update` 提示 **`MIGRATION REQUIRED`**（项目版本和 CLI 之间存在 breaking
  变更），必须运行 `trellis update --migrate`——否则 breaking
  版本里改名或挪位置的文件会留在旧路径上不动。
</Warning>

完整的 `upgrade` / `update` / `--migrate` 说明见[命令 §1.2](/zh/start/everyday-use#1-2-命令)。

### 平台配置

`trellis init` 为每个平台写入各自的配置目录。`.trellis/` 下的核心概念跨平台一致，差异在于 command、skill、sub-agent、hook 的交付方式。

| 平台            | 配置目录                                                                     |
| --------------- | ---------------------------------------------------------------------------- |
| **Claude Code** | `.claude/commands/trellis/`、`agents/`、`skills/`、`hooks/`                  |
| **Cursor**      | `.cursor/commands/`、`agents/`、`skills/`、`hooks/`                          |
| **OpenCode**    | `.opencode/commands/trellis/`、`agents/`、`skills/`、`plugins/`、`hooks/`    |
| **Codex**       | `.codex/agents/`、`skills/`、`hooks/` + 仓库根 `AGENTS.md`                   |
| **Kiro**        | `.kiro/agents/`、`skills/`、`hooks/`                                         |
| **Gemini CLI**  | `.gemini/commands/trellis/`、`agents/`、`skills/`、`hooks/`                  |
| **Qoder**       | `.qoder/commands/`、`agents/`、`skills/`、`hooks/`                           |
| **CodeBuddy**   | `.codebuddy/commands/trellis/`、`agents/`、`skills/`、`hooks/`               |
| **Copilot**     | `.github/copilot/`、`prompts/`、`agents/`、`skills/`、`hooks/`               |
| **Droid**       | `.factory/commands/trellis/`、`droids/`、`skills/`、`hooks/`                 |
| **Pi Agent**    | `.pi/prompts/`、`skills/`、`agents/`、`extensions/trellis/`、`settings.json` |
| **Oh My Pi**    | `.omp/commands/`、`skills/`、`agents/`、`extensions/trellis/`                |
| **Kilo**        | `.kilocode/workflows/`、`skills/`                                            |
| **Antigravity** | `.agent/workflows/`、`skills/`                                               |
| **Devin**       | `.devin/workflows/`、`skills/`                                               |

`.agents/skills/` 是一份跨平台共享层（[agentskills.io](https://agentskills.io) 规范），`trellis init` 会把所有 skill 都写一份到这里，供 Amp、Cline、Deep Agents、Firebender、Warp 等遵循 `.agents/skills/` 规范的 agent 直接读取。

### init 场景对照

`trellis init` 根据 `.trellis/` 与 `.trellis/.developer` 的存在状态自动分派。按你的情境挑对应的命令：

| 场景                     | 命令                                                            | 产物                                                                                                |
| ------------------------ | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **首次 init 项目**       | `trellis init -u your-name --claude`                            | 创建 `.trellis/` 骨架 + bootstrap task `00-bootstrap-guidelines`，引导填项目 spec                   |
| **往已有项目加新平台**   | `trellis init --cursor`（或不带参数走交互式，会列出未配置平台） | 在现有 `.trellis/` 上铺新平台配置目录；不产生 task                                                  |
| **新开发者加入已有项目** | `trellis init -u their-name`                                    | 生成 joiner 引导 task `00-join-<slug>`，引导读 workflow + spec；准备开始时在当前 AI 会话里 start 它 |
| **同一开发者换机器**     | 同上                                                            | 也会创建 joiner task，因为 `.developer` 是单 checkout 配置，不会提交到 Git                          |
| **同一人同机器 re-init** | `trellis init -u your-name`                                     | no-op —— `.trellis/` 与 `.developer` 都在，啥都不做                                                 |

`--force` / `--skip-existing` 只影响 **有冲突的文件**怎么处理（强制覆盖 / 跳过），不改变 init 的分派逻辑本身。

<Note>
  **判据信号**：`.trellis/.developer` 是 gitignored 的 per-checkout 身份文件（天然不进 git），所以新克隆的 checkout 永远没有它 —— 这是判断"新开发者"的干净信号。`.trellis/workspace/<name>/` 进 git，不能作为判据。
</Note>

### 基本流程

描述你要做的事。AI 会判断是否需要 Trellis 任务。范围清楚、风险低的小型
工作可以直接处理；范围更大的工作则使用任务路线。如果创建任务需要你的
确认，AI 会先征求同意。路线和阶段职责见 [Trellis 工作流如何运行](/zh/start/how-it-works)。

```text
# 1. 描述你要做什么
"新增用户登录功能"

# 2. AI 判断范围并选择与任务相称的路线

# 3. Trellis 任务先与你核对需求，再依据工作内容和证据选择后续阶段

# 4. finish-work 记录会话进度；任务完成由单独的生命周期操作处理
/trellis:finish-work
```

<Note>
  Agent-capable 平台通过 SessionStart hook、prompt hook、extension、agent 文件和 skill 的组合加载
  Trellis 上下文。Codex 和 Claude-style 平台不同：它依赖 `AGENTS.md` 加 `UserPromptSubmit` hook，
  no-task breadcrumb 会提示 AI 读取 `trellis-start`。只有 Kilo / Antigravity / Devin 这类 agent-less
  平台会发 `/trellis:start`（或 `/start.md`）作为显式入口。
</Note>

## 你的第一个任务

### 启动会话

<Tabs>
  <Tab title="General">
  打开终端。有 hook 支持的平台会通过紧凑 SessionStart payload 给 AI 足够的 Trellis 上下文来判断下一步：

- `workflow.md` 的紧凑 Phase Index
- 身份、git 状态、活跃任务列表
- spec index 路径
- task artifact context order

**直接描述任务即可**。

怀疑自动注入没跑、想重新加载上下文，就新开一个会话，或者让 AI 读取一次
`trellis-start` skill。这类平台通常没有 `/trellis:start` slash 命令，因为启动
路径已经负责 orient。

  </Tab>
  <Tab title="Codex">
  **必须在 `~/.codex/config.toml` 开启 hook，否则聊天界面输入 `/` 检索不到 Trellis 的三大命令（`/start`、`/finish-work`、`/continue`），也无法用 `/start` 启动会话。**

```toml
[features]
hooks = true   # Codex 0.129+。旧版用 `codex_hooks = true`。
```

Codex 0.129+ 还要在 TUI 里跑一次 `/hooks` 命令，审批 Trellis 安装的 `UserPromptSubmit` hook，否则 hook 不会激活、Trellis 的 command / skill 不会出现在 `/` 菜单、workflow 指引也不会自动注入。即便没开，Trellis 内置 fallback 会让 AI 手动读 `trellis-start` skill（靠 `AGENTS.md` prelude），上下文仍在——但你没法从 `/` 里点用 Trellis 命令，体验明显下降。

之后直接描述任务即可。Codex 会自动读取 `AGENTS.md`，`UserPromptSubmit`
hook 会注入当前 workflow-state breadcrumb。没有 active task 时，这段 breadcrumb
可能包含 `<trellis-bootstrap>`，提示 AI 读取一次 `trellis-start`。

  </Tab>
  <Tab title="Kiro">
  Kiro CLI 通过当前启用的 `trellis` agent 加载 Trellis，包括 `agentSpawn` 和 `userPromptSubmit` hook。使用 `/agent swap trellis` 或 `kiro-cli settings chat.defaultAgent trellis` 选中它。Kiro IDE 会获得默认启用的 `promptSubmit` hook，须在 Agent Hooks 中确认信任与启用状态。描述新请求进入需求核对，已有任务由 `trellis-continue` 恢复。尚待真实 Kiro 运行时核验的限制见[多平台支持](/zh/advanced/multi-platform)。
  </Tab>
  <Tab title="Kilo / Antigravity / Devin">
  这三个平台只有 workflow + skill，没有 hook 和 sub-agent。入口：
  - Kilo：`/start.md`
  - Antigravity：打开 `.agent/workflows/start.md`
  - Devin：`/trellis-start`

AI 执行 workflow 里写的步骤：读 workflow.md、跑 `get_context.py`、读 spec 索引、询问你想做什么。后续的 implement / check 阶段会在主会话里内联跑，而不是 spawn sub-agent。

  </Tab>
</Tabs>

### 示例：从零开始新项目

这是新建产品、服务、SDK、包或内部工具时的第一轮 Trellis 流程。

真实情况：要开发一个 B2B Dashboard，包含登录、团队管理、计费和分析页面。希望项目约定能逐步沉淀，避免每次会话都重新讨论已经确定的内容。

起始 prompt：

```text
我准备从零开始开发一个 B2B Dashboard。请先和我核对启动首个任务所需的产品目标、范围和技术选择，再根据已确认的决定创建任务。只记录当前项目确实需要的约定，不要预先补齐无关的 spec。
```

`trellis init` 会创建基础 spec 模板和 `00-bootstrap-guidelines` 任务。模板只是起点：保留或编写与项目相关、且有已确认决策或代码证据支持的约定即可，不必在开始有用工作前填完所有文件。已有代码的项目可选用内置的 `trellis-spec-bootstrap` Skill 梳理现有模式并起草 spec，再逐项审阅。全新项目则记录当前启动所需的决定。

后续按 `workflow.md` 中适用于该任务的路线推进。只有在能提供价值时才进入决策空间构造与归并阶段、解决方案设计与收敛阶段；实施前必须接受实施合同，并另行取得授权。交付验证和审查完成后，通过 Trellis CLI 完成任务。`/trellis:finish-work` 只记录会话进度，不会完成任务。

### AI 建任务并开发

你说："新增用户登录功能"。AI 会判断是否需要 Trellis 任务，并在需要你
批准时先征求同意。对于 Trellis 任务，AI 会先与你核对需求，再根据
`workflow.md` 选择适用阶段：

```text
目标探索与需求核对阶段
  与用户确认目标、范围、验收条件、约束和证据。

决策空间构造与归并阶段（需要时）
  比较方案，并与用户解决实质性决策。

解决方案设计与收敛阶段（需要时）
  接受分析结论或完整的实施合同；开始实施仍需单独授权。

任务实施与测试验证阶段（获得授权后）
  按已接受的合同推进并验证改动。

交付审查与现场收尾阶段
  审查交付，解决缺口或记录剩余工作，再通过 Trellis CLI 完成或取消任务。
```

上述路线按任务需要选择，并非必须逐项执行的清单。`/trellis:continue` 根据
Trellis CLI 记录的路线恢复当前任务；不能仅凭任务状态或产物是否存在推断当前阶段。若证据表明某些阶段不会带来价值，路线可以省略这些阶段。

### 结束会话

```
/trellis:finish-work
```

`finish-work` 会在工作区日志中记录会话进度，不会完成或归档任务。交付审查与
现场收尾接受结果后，可通过 `task.py complete <task>` 完成任务；稳定版任务记录
仍保留在 `.trellis/tasks/`。[Beta 任务目录治理](/zh/beta/guides/task-layout)新增按状态自动移动。

### 跨会话记忆

下次打开会话，SessionStart hook（或平台 prelude）会读你的 workspace journal 和活跃任务列表，AI 能回忆起上次做了什么：

```
AI："Alice 好，你上次完成了用户登录功能（commit abc1234），
     包含 LoginForm 组件、JWT 中间件、users 表。
     接下来想干什么？"
```

Journal 存在 `.trellis/workspace/{name}/journal-N.md`；每次 `/trellis:finish-work` 都会追加一条。Trellis 内部会按 AI 会话/窗口记录各自的当前 task，下次进同一个会话能直接接上；`task.py finish` 会清掉这个指针。

## 远程 Spec 模板

不用从零写 spec，在 init 时拉取预置的 spec 模板：

### 按源码生成规范与显式来源

```bash
# 初始化索引和通用 guides，随后使用 trellis-spec-bootstrap
trellis init -u your-name

# 可选：明确指定 registry 及其中的模板 ID
trellis init -u your-name --registry gh:myorg/specs --template my-template
```

从 `0.7.2-beta.0` 起，init 不再隐式访问 Marketplace Spec 来源。内置索引和通用 guides 是分析引导，不是已经核实的项目规则；通过 `trellis-spec-bootstrap` 按实际源码形成适用的 package/layer 规范，遵守项目语言并保留自定义规范，不生成无关技术主题。已有显式 `registry.spec` 仍由用户管理，本次不会静默改写其来源。

### 自定义 Registry（`--registry`）

从你自己的 GitHub / GitLab / Bitbucket 仓库拉取 spec：

```bash
# 直接下载：仓库目录变成 .trellis/spec/
trellis init --registry gh:myorg/myrepo/my-team-spec

# Marketplace 模式：仓库里有 index.json 定义多模板
trellis init --registry gh:myorg/myrepo/marketplace

# 从自定义 marketplace 选特定模板
trellis init --registry gh:myorg/myrepo/marketplace --template my-template

# 指定分支
trellis init --registry gh:myorg/myrepo/specs#develop

# GitLab 或 Bitbucket
trellis init --registry gitlab:myorg/myrepo/specs
trellis init --registry bitbucket:myorg/myrepo/specs
```

**Source 格式**：`provider:user/repo[/subdir][#ref]`

| Provider  | 前缀               |
| --------- | ------------------ |
| GitHub    | `gh:` 或 `github:` |
| GitLab    | `gitlab:`          |
| Bitbucket | `bitbucket:`       |

不写 ref（branch/tag）时默认 `main`。

### 已有 spec 的处理

`.trellis/spec/` 已存在时，用 strategy flag：

| Flag          | 行为                     |
| ------------- | ------------------------ |
| `--overwrite` | 删除现有 spec 目录再下载 |
| `--append`    | 只拷贝不存在的文件       |
| _（都不传）_  | 交互式询问怎么处理       |

### 构建自定义 Marketplace

在仓库根目录创建 `index.json`：

```json
{
  "version": 1,
  "templates": [
    {
      "id": "my-backend-spec",
      "type": "spec",
      "name": "My Backend Spec",
      "description": "团队后端约定",
      "path": "marketplace/specs/my-backend-spec",
      "tags": ["backend", "node"]
    }
  ]
}
```

`path` 相对仓库根目录。目前只支持 `type: "spec"`。

### 私有仓库

私有仓库要设置 `GIGET_AUTH` 环境变量，值是 personal access token：

```bash
GIGET_AUTH=ghp_xxxxx trellis init --registry gh:myorg/private-repo/specs
```

GitHub fine-grained token 需要 **Contents** 和 **Metadata** 的读权限。
