## 1. 命令与 Skill 参考

Trellis CLI 按任务需要选择业务阶段。每个阶段 Skill 提供自己的流程和图示；任务记录保存所选路线和阶段接受结果。宿主提供的会话命令与任务完成相互独立。

### 1.1 总览

| 入口       | 名称                                              | 用途                                                 |
| ---------- | ------------------------------------------------- | ---------------------------------------------------- |
| 会话命令   | `/trellis:start`                                  | 宿主不会自动注入上下文时，手动加载任务上下文。       |
| 会话命令   | `/trellis:continue`                               | 根据任务记录的路线和下一项适用活动继续当前任务。     |
| 会话命令   | `/trellis:finish-work`                            | 记录会话进度；不完成任务，也不归档任务。             |
| 任务 CLI   | `task.py phase`                                   | 查看和更新任务的业务阶段路线及阶段记录。             |
| 任务 CLI   | `task.py complete` / `task.py cancel`             | 在收尾时完成已接受的任务，或记录取消。               |
| 阶段 Skill | `trellis-goal-exploration-and-requirements`       | 目标探索与需求核对阶段：建立经用户确认的需求基线。   |
| 阶段 Skill | `trellis-decision-space-construction-and-merging` | 决策空间构造与归并阶段：识别并整理实质决策。         |
| 阶段 Skill | `trellis-solution-design-and-convergence`         | 解决方案设计与收敛阶段：接受分析结论或实施合同。     |
| 阶段 Skill | `trellis-task-implementation`                     | 任务实施与测试验证阶段：实施并验证已获授权的合同。   |
| 阶段 Skill | `trellis-delivery-review-and-closeout`            | 交付审查与现场收尾阶段：审查交付并确定任务处置结果。 |

宿主提供的会话命令可能不同。任务会按需选择五个业务阶段；阶段不由任务生命周期状态表示。路线选择和组件职责见[工作流如何运行](/zh/start/how-it-works)。

### 1.2 命令

#### 1.2.1 三个版本：`upgrade` vs `update`

Trellis 同时追踪三个独立的版本。搞清楚谁是谁，就理解了为什么升级是两步：

1. **已发布版** — npm 上的最新版本
2. **本地 CLI** — 你全局安装的 `trellis` 命令
3. **项目版** — 你 repo 里 `.trellis/` 的模板版本

- `trellis upgrade` 把 **② → ①**（升级全局 CLI 本体）
- `trellis update` 把 **③ → ②**（把当前项目同步到本地 CLI 的版本）

所以完整升级 = 先 `trellis upgrade`（CLI）再 `trellis update`（项目）。`trellis update` 最多只能把项目抬到本地 CLI 的版本——CLI 自己旧了，得先升 CLI。

#### 1.2.2 `trellis upgrade`：升级 CLI package

全局安装的 Trellis CLI 落后于已发布版本时使用：

```bash
trellis upgrade              # 跟随当前 channel：latest / beta / rc
trellis upgrade --tag beta   # 从稳定版切换到最新 beta
trellis upgrade --tag latest # 显式安装最新稳定版
trellis upgrade --dry-run    # 只打印 npm 命令，不实际执行
```

<Note>
  较旧版本可能没有 `trellis upgrade`。可以直接安装当前包： `npm install -g
  @pennixrv/trellis@latest`，之后再用 `trellis upgrade` 更新。
</Note>

`trellis upgrade` 升级的是全局 CLI package，不会改当前项目里的文件。CLI 升级后，如果某个 Trellis 项目需要同步新的 workflow、hook、skill 或平台文件，再在该项目里运行 `trellis update`。

#### 1.2.3 `trellis update`：把项目同步到 CLI 版本

升级完 CLI 后，在 Trellis 项目里运行。它把 `.trellis/` 模板和平台文件（hook、skill、command）同步到本地 CLI 的版本：

```bash
trellis update               # 把项目同步到本地 CLI 的模板版本
trellis update --dry-run     # 只预览改动，不实际执行
trellis update --migrate     # 同时执行文件迁移（改名 / 挪位置 / 删除）
```

`trellis update` 只碰你没改过的文件——自定义内容不会丢，改动前还会自动创建带时间戳的备份。

<Warning>
  如果 update 输出最后出现 **`MIGRATION REQUIRED`**（项目版本和 CLI 之间存在 breaking 变更，比如
  `0.4.0 → 0.6.5`），必须运行 `trellis update --migrate`。不加 `--migrate` 的话，breaking
  版本里改名或挪位置的文件**不会**被移动——项目里会留着一堆旧路径的过期文件，和新模板混在一起。可以先用
  `--dry-run` 预览 `--migrate` 会做什么。
</Warning>

#### 1.2.4 `/trellis:start`：开启会话

如果平台不自动注入上下文就手动跑一下。Hook 或 extension 可用的平台（Claude Code、Cursor、OpenCode、Gemini、Qoder、CodeBuddy、Copilot、Droid、Pi Agent，以及开了 `features.hooks = true` 的 Codex —— 旧版用 `codex_hooks = true`）有 SessionStart hook 或 extension，打开终端就自动执行，所以通常不会安装用户可见的 `start` 命令。

行为：

1. 读 `.trellis/workflow.md`，让 AI 清楚工作流契约。
2. 跑 `get_context.py` 拿到开发者身份、git 状态、活跃任务。
3. 读 spec 索引（monorepo 场景下按 package 读）。
4. 汇报上下文并询问你想做什么。

AI 做的任务分类：

| 类型          | 判断依据                           | 流程                                                                 |
| ------------- | ---------------------------------- | -------------------------------------------------------------------- |
| 简单对话      | 问答、解释、查询、讨论，不改仓库   | 默认不建任务。如果任务可能有帮助，只问本回合是否需要创建任务。       |
| Inline 小任务 | 当前 turn 可以理解和验证的局部改动 | 只问本回合是否需要创建任务。用户说不需要时，跳过 Trellis 并 inline。 |
| 完整任务      | 多文件改动或需要持久规划的工作     | 询问是否可以创建 Trellis task 并进入 planning。                      |

用户拒绝复杂任务建 task 时，AI 应该澄清范围或建议拆小，而不是做大范围 inline 实现。

#### 1.2.5 `/trellis:finish-work`：记录会话进度

此会话命令会将进度写入 `.trellis/workspace/`。它不会改变任务状态、业务阶段状态或实施授权。任务应在交付审查与现场收尾阶段通过 Trellis CLI 完成或取消；此操作不会将任务记录移动到归档目录。

#### 1.2.6 `/trellis:continue`：当前任务内推进下一步

`continue` 用于继续当前任务。Trellis CLI 将任务生命周期状态与 `task.json.meta.task_workflow` 中保存的业务阶段路线和阶段记录分开读取；当前阶段 Skill 提供对应流程。

典型一次 task 的对话：

1. 用自然语言描述工作。适合创建 Trellis 任务时，先明确目标并与用户核对当前需求。
2. 按适用性选择有序阶段路线；省略可选阶段时记录依据，仅在需要时进入方案设计。
3. 只有实施合同获接受并另行取得实施授权后，才开始实施；按需读取项目规范并执行验证。
4. 审查当前交付、解决或记录实质缺口，再通过 Trellis CLI 完成或取消任务。需要时单独记录会话进度。

路线按任务确定。`continue` 可以恢复当前路线；任务记录会将业务阶段进度与任务生命周期状态分开保存。

### 1.3 阶段 Skill 与协作组件

五个阶段 Skill 分别是 `trellis-goal-exploration-and-requirements`、`trellis-decision-space-construction-and-merging`、`trellis-solution-design-and-convergence`、`trellis-task-implementation` 和 `trellis-delivery-review-and-closeout`。每个 Skill 都包含本阶段的流程和图示。支持 Skill、Trellis Teamwork、Paseo 和宿主工具按各自职责参与；任务路线不要求每个任务都调用所有组件。路线和组件职责见[工作流如何运行](/zh/start/how-it-works)与[架构概览](/zh/advanced/architecture)。

支持性 Skill 包括 `trellis-teamwork`、`trellis-session-insight`、`trellis-spec-bootstrap` 和 `trellis-meta`。任务需要时再按职责使用；这些 Skill 都不管理任务阶段状态。`trellis-research`、`trellis-implement` 和 `trellis-check` 是子代理定义，不是 Skill。

## 2. 任务管理全流程

### 2.1 任务生命周期

```
创建任务 → 确认需求 → 选择适用的阶段路线 → 接受结果并在需要时授权实施 → 实施与验证 → 审查交付 → 完成或取消任务

create：                任务目录 + task.json + 默认 prd.md
plan artifacts：        每个任务都有 prd.md；复杂任务 start 前补 design.md + implement.md
optional jsonl context： 需要稳定注入 spec 或 research 文件时，AI 填 implement/check 上下文
start：                 把当前 AI 会话/窗口的任务标记为 in_progress
implement/check：       开发与验证循环
finish：                清除当前 AI 会话/窗口的任务
完成或取消：            通过 Trellis CLI 更新任务生命周期状态
```

`task.py create` 会创建任务目录、`task.json` 和默认的 `prd.md`，并要求提供非空描述。任务生命周期状态与业务阶段状态相互独立。`task.py start` 将任务设为当前任务，但本身不授予实施权限。所选路线和阶段记录保存在 `task.json.meta.task_workflow` 中。

### 2.2 `task.py` 子命令

#### 2.2.1 创建任务

```bash
# 创建任务
TASK_DIR=$(./.trellis/scripts/task.py create "新增用户登录" \
  --slug user-login \          # 目录名后缀（可选，不写自动生成）
  --assignee alice \           # 负责人（可选）
  --priority P1 \              # 优先级：P0/P1/P2/P3（可选，默认 P2）
  --description "实现 JWT 登录")  # 必填

# 创建的目录：.trellis/tasks/02-27-user-login/
# 创建的文件：task.json、prd.md
# sub-agent 平台上还可能创建 implement.jsonl + check.jsonl
```

#### 2.2.2 上下文配置

```bash
# sub-agent 平台上 implement.jsonl + check.jsonl 会在 task.py create 时
# seed 好——每个文件起手一行自描述 {"_example": "..."}，可保留也可删除。

# curate 条目：在编辑器里改 jsonl，或用 add-context：
./.trellis/scripts/task.py add-context "$TASK_DIR" implement \
  ".trellis/spec/backend/index.md" "后端开发指南"
./.trellis/scripts/task.py add-context "$TASK_DIR" check \
  ".trellis/spec/cli/unit-test/conventions.md" "单测约定"
# target：implement | check（自动补 .jsonl）
# path：文件或目录路径——add-context 自动识别，目录会 type="directory"
#
# jsonl 里放什么：任务相关的 spec 文件（.trellis/spec/**/*.md）和 research
# 文件（$TASK_DIR/research/*.md）。不要放代码路径——代码在任务实施与测试验证阶段
# 读，不在这里预注册。

# 看有哪些 spec 可选
./.trellis/scripts/get_context.py --mode packages
# 可选：--package PACKAGE   （monorepo 必填，选 spec/<pkg>/ 根）

# 校验 implement.jsonl + check.jsonl 里引用的文件都存在
./.trellis/scripts/task.py validate "$TASK_DIR"

# 查看所有 JSONL 条目
./.trellis/scripts/task.py list-context "$TASK_DIR"
```

<Note>
  `task.py add-context` 只写 `implement.jsonl` / `check.jsonl`。调研发现放在 `{TASK_DIR}
  /research/*.md`；只有后续 sub-agent 工作前必须读取时，才把这些文件加入 implement/check manifest。
</Note>

#### 2.2.3 任务控制

```bash
# 设为当前 AI 会话/窗口的任务
# 写入 .trellis/.runtime/sessions/<session-key>.json
./.trellis/scripts/task.py start "$TASK_DIR"

# 清除当前 AI 会话/窗口的任务
./.trellis/scripts/task.py finish

# 设置 Git 分支名
./.trellis/scripts/task.py set-branch "$TASK_DIR" "feature/user-login"

# 设置 PR 目标分支
./.trellis/scripts/task.py set-base-branch "$TASK_DIR" "main"

# 设置 scope（用在 commit message：feat(scope): ...）
./.trellis/scripts/task.py set-scope "$TASK_DIR" "auth"
```

#### 2.2.4 父子任务（subtasks）

一个任务可以有子任务。子任务是磁盘上独立的任务目录——有自己的 `prd.md`、JSONL 文件、status；父任务只是引用它们做分组。

```bash
# 方式 A：在父任务下直接建子任务
./.trellis/scripts/task.py create "JWT middleware" \
  --slug jwt-middleware \
  --parent 02-27-user-login

# 方式 B：把两个已有任务链起来
./.trellis/scripts/task.py add-subtask \
  02-27-user-login \                # 父任务目录
  02-28-jwt-middleware              # 子任务目录

# 解除关联（不会删除任何任务）
./.trellis/scripts/task.py remove-subtask \
  02-27-user-login 02-28-jwt-middleware
```

对 `task.json` 的影响：

- 父任务的 `children: [<子任务目录名>, ...]` 追加子任务名。
- 子任务的 `parent: "<父任务目录名>"` 被设置。
- `task.py list` 把子任务缩进显示在父任务下面，同时打 `[已完成/总数]`，方便一眼看进度。

<Note>
  父子关系走 `parent` 和 `children` 字段。`task.json` 里还有一个 `subtasks`
  字段，和它们完全无关——`subtasks` 是**单个任务内部的 todo checklist**（name + status 对），主要由
  bootstrap 任务使用。别混。
</Note>

#### 2.2.5 任务管理

```bash
# 列出活跃任务
./.trellis/scripts/task.py list
./.trellis/scripts/task.py list --mine            # 只看自己的
./.trellis/scripts/task.py list --status review   # 按状态过滤

# 交付审查与现场收尾阶段接受结果后完成任务
./.trellis/scripts/task.py complete user-login

# 任务不再推进时取消；必须提供原因和证据引用
./.trellis/scripts/task.py cancel user-login --reason "已被其他方案取代" --evidence-ref "任务决策记录"
```

### 2.3 `task.json` Schema

`task.py create` 当前实际写出的结构（详见 `.trellis/scripts/common/task_store.py`）：

```json
{
  "id": "02-27-user-login",
  "name": "user-login",
  "title": "新增用户登录",
  "description": "实现 JWT 登录流程",
  "status": "planning",
  "dev_type": null,
  "scope": null,
  "package": null,
  "priority": "P1",
  "creator": "alice",
  "assignee": "alice",
  "createdAt": "2026-02-27",
  "completedAt": null,
  "branch": null,
  "base_branch": "main",
  "worktree_path": null,
  "commit": null,
  "pr_url": null,
  "subtasks": [],
  "children": [],
  "parent": null,
  "relatedFiles": [],
  "notes": "",
  "meta": {}
}
```

字段会随任务进展被填上：

- `dev_type` / `scope` / `package` → 通过 `task.py set-scope` 或直接编辑 `task.json` 写入；没有自动 setter
- `branch` → `task.py set-branch` 设置
- `status` → 任务生命周期状态，不能表示当前业务阶段
- `completedAt` → 在收尾结果获接受后由 `task.py complete` 设置
- `parent` / `children` → `task.py create --parent` 或 `add-subtask` 设置

<Note>
  任务字段和元数据会随任务类型及生命周期变化。应以当前任务 CLI 和任务工作流记录为准，
  不要把此示例当作完整 schema。
</Note>

早期版本创建的任务可能少某些字段（如 `package` 支持前的任务没有 `"package"`），`task.py` 把缺失字段按 null 处理，不会出错。

**任务生命周期与业务阶段状态**：

```
task.py create   →  status: "planning"
task.py start    →  设置当前任务；获授权准入后再进入实施状态
task.py complete →  收尾结果获接受后设为 "completed"
task.py cancel   →  提供原因和证据引用后设为 "cancelled"
```

所选业务阶段及其状态保存在 `meta.task_workflow` 中，不由 `task.json.status` 表示。运行 `task.py phase show <task>` 和 `task.py --help` 查看当前阶段记录及支持的操作。完成任务不会将任务记录移动到归档目录。

### 2.4 JSONL 上下文配置实战

#### 2.4.1 创建时生成初始条目，按需整理上下文

在 sub-agent 平台上，`task.py create` 会在两个 jsonl 里各写**一行 seed**：

```jsonl
# task.py create 刚跑完的 implement.jsonl
{"_example": "Fill with {\"file\": \"<path>\", \"reason\": \"<why>\"}. Put spec/research files only — no code paths. Run `python3 .trellis/scripts/get_context.py --mode packages` to list available specs. Delete this line when done."}
```

这一行是给 AI 看的填写说明。它没有 `file` 字段，所有下游消费方（hook / prelude / validate / list-context）都会跳过；准备任务上下文时，AI 会将其替换为真实条目。

**AI curate 之后的 implement.jsonl 样例**（monorepo `dev_type=backend`）：

```jsonl
{"file": ".trellis/spec/guides/index.md", "reason": "跨包思维指引"}
{"file": ".trellis/spec/cli/backend/index.md", "reason": "后端开发指南——本次改动涉及 Python 脚本"}
{"file": ".trellis/spec/cli/backend/script-conventions.md", "reason": "脚本规范"}
{"file": ".trellis/tasks/.../research/auth-library-comparison.md", "reason": "三方库选型依据"}
```

**jsonl 该放什么**：

- **Spec 文件**（`.trellis/spec/<pkg>/<layer>/index.md` + 具体 guideline 文件）：和任务相关的规范
- **Research 文件**（`{TASK_DIR}/research/*.md`）：sub-agent 要参考的调研产出

**不该放什么**：

- 代码文件（`src/**`、`packages/**/*.ts` 等）——在实施时读取，不在这里预先登记
- 即将要改的文件——同上

不使用 JSONL 上下文时，由主会话或相关 Skill 直接读取适用的项目规范。

#### 2.4.2 添加自定义上下文

```bash
# 添加实现阶段 spec 上下文
./.trellis/scripts/task.py add-context "$TASK_DIR" implement \
  ".trellis/spec/cli/backend/script-conventions.md" "本任务涉及脚本规范"

# 添加 planning 阶段产出的 research
./.trellis/scripts/task.py add-context "$TASK_DIR" implement \
  "$TASK_DIR/research/auth-library-comparison.md" "三方库选型依据"

# 添加 check 上下文
./.trellis/scripts/task.py add-context "$TASK_DIR" check \
  ".trellis/spec/guides/cross-layer-thinking-guide.md" "跨层验证"
```

### 2.5 任务生命周期 Hook

你可以配置 shell 命令，在任务生命周期事件上自动跑。用于对接 Linear、发 Slack、触发 CI 等。

#### 2.5.1 配置

在 `.trellis/config.yaml` 加 `hooks` 块：

```yaml
hooks:
  after_create:
    - 'python3 .trellis/scripts/hooks/linear_sync.py create'
  after_start:
    - 'python3 .trellis/scripts/hooks/linear_sync.py start'
  after_finish:
    - "echo 'Task finished'"
  after_complete:
    - 'python3 .trellis/scripts/hooks/linear_sync.py complete'
```

<Note>默认 `config.yaml` 里 hooks 段是**注释掉**的。取消注释并编辑即可激活。</Note>

#### 2.5.2 支持的事件

| 事件             | 触发时机                          | 用途                            |
| ---------------- | --------------------------------- | ------------------------------- |
| `after_create`   | `task.py create` 完成             | 在项目追踪工具里建 issue        |
| `after_start`    | `task.py start` 设置当前会话任务  | 更新 issue 状态到 "In Progress" |
| `after_finish`   | `task.py finish` 清除当前会话任务 | 通知团队、触发 review           |
| `after_complete` | `task.py complete` 完成任务       | 标记 issue 为 "Done"            |

#### 2.5.3 环境变量

每个 hook 收到：

| 变量             | 值                          |
| ---------------- | --------------------------- |
| `TASK_JSON_PATH` | 任务 `task.json` 的绝对路径 |

其他环境变量从父进程继承。

#### 2.5.4 执行行为

- **工作目录**：仓库根
- **Shell**：命令通过系统 shell 运行（`shell=True`）
- **失败不阻断**：失败的 hook 在 stderr 打印 `[WARN]`，但不阻止任务操作完成
- **顺序**：同一事件有多个 hook 按列表顺序执行；一个失败不跳过其他
- **stdout 不显示**：诊断输出用 stderr

#### 2.5.5 示例：Linear Sync Hook

Trellis 原生带有 `.trellis/scripts/hooks/linear_sync.py` 示例 hook，把任务生命周期事件同步到 [Linear](https://linear.app)。

**行为**：

| 操作       | 触发             | 效果                                                              |
| ---------- | ---------------- | ----------------------------------------------------------------- |
| `create`   | `after_create`   | 从 task.json 建 Linear issue（title、priority、assignee、parent） |
| `start`    | `after_start`    | 把关联 issue 更新到 "In Progress"                                 |
| `complete` | `after_complete` | 把关联 issue 更新到 "Done"                                        |
| `sync`     | 手动             | 把 `prd.md` 内容推到 Linear issue 描述                            |

**前置**：

1. 装 [`linearis`](https://www.npmjs.com/package/linearis) CLI 并设置 `LINEAR_API_KEY`
2. 创建 `.trellis/hooks.local.json`（gitignored）放团队配置：

```json
{
  "linear": {
    "team": "ENG",
    "project": "我的项目",
    "assignees": {
      "alice": "linear-user-id-for-alice"
    }
  }
}
```

Hook 把 Linear issue id 写回 `task.json` 的 `meta.linear_issue`（如 `"ENG-123"`），保证后续事件幂等。

## 3. 规范编写指南

### 3.1 Spec 目录结构和分层

#### 3.1.1 `trellis init` 默认结构

`trellis init` 会写一个骨架：`frontend/` + `backend/` + `guides/`，里面全是**空占位模板**（标注 "(To be filled by the team)"）。这些模板原样注入 sub-agent 是没用的。

```
.trellis/spec/
├── frontend/                    # 前端规范（占位）
│   ├── index.md                 #   索引：列出所有规范及状态
│   ├── component-guidelines.md  #   组件规范
│   ├── hook-guidelines.md       #   Hook 规范
│   ├── state-management.md      #   状态管理
│   ├── type-safety.md           #   类型安全
│   ├── quality-guidelines.md    #   质量指南
│   └── directory-structure.md   #   目录结构
│
├── backend/                     # 后端规范（占位）
│   ├── index.md
│   ├── database-guidelines.md
│   ├── error-handling.md
│   ├── logging-guidelines.md
│   ├── quality-guidelines.md
│   └── directory-structure.md
│
└── guides/                      # 思维指南
    ├── index.md
    ├── cross-layer-thinking-guide.md
    └── code-reuse-thinking-guide.md
```

首次初始化时，`trellis init` 会创建一个 **bootstrap 任务**（`00-bootstrap-guidelines`），用于组织项目初始配置。根据项目需要补充上下文和规范；`trellis-spec-bootstrap` 可以协助起草结合代码的规范。无需默认填满所有占位模板。

#### 3.1.2 这套结构只是约定

`frontend/` 和 `backend/` 没有任何魔法。Trellis 扫描 `.trellis/spec/` 下的一级目录，只要目录里有 `index.md` 就把它当作一个 spec 层注册。你按项目实际怎么切就怎么命名——按运行时、按 package、按职责都行，每层有自己的 `index.md` 就够。

Trellis 本身用的是另一种结构（monorepo、按 package）：

```
.trellis/spec/                                # Trellis 自己的 spec 树
├── cli/                                      # Package: CLI
│   ├── backend/
│   │   └── index.md                          #   ← 通过 index.md 注册为一层
│   └── unit-test/
│       └── index.md                          #   ← 又一层
│
├── docs-site/                                # Package: 文档站
│   └── docs/
│       └── index.md                          #   ← 单层 package
│
└── guides/                                   # 跨 package 的思维指南
    ├── index.md
    ├── cross-layer-thinking-guide.md
    ├── cross-platform-thinking-guide.md
    └── code-reuse-thinking-guide.md
```

顶层没有 `frontend/` 或 `backend/`，因为仓库是按 package 切的。Trellis 唯一硬性约定就是"一层 = 带 `index.md` 的目录"，其他随你。

### 3.2 从空模板到完整规范

`trellis init` 会生成空模板，标记 "(To be filled by the team)"。填充步骤：

**Step 1**：从实际代码中提取模式

```bash
# 看看现有代码是怎么组织的
ls src/components/     # 组件结构
ls src/services/       # 服务结构
```

**Step 2**：写下你的约定

```markdown
# Component Guidelines

## File Structure

- One component per file
- Use PascalCase for filenames: `UserProfile.tsx`
- Co-locate styles: `UserProfile.module.css`
- Co-locate tests: `UserProfile.test.tsx`

## Patterns

#### Required

- Functional components + hooks (no class components)
- TypeScript with explicit Props interface
- `export default` for page components, named export for shared

#### Forbidden

- No `any` type in Props
- No inline styles (use CSS Modules)
- No direct DOM manipulation
```

**Step 3**：添加代码示例

````markdown
#### Good Example

```tsx
interface UserProfileProps {
  userId: string;
  onUpdate: (user: User) => void;
}

export function UserProfile({ userId, onUpdate }: UserProfileProps) {
  // ...
}
```

#### Bad Example

```tsx
// Don't: no Props interface, using any
export default function UserProfile(props: any) {
  // ...
}
```
````

**Step 4**：更新 index.md 状态

```markdown
| Guideline            | File                    | Status     |
| -------------------- | ----------------------- | ---------- |
| Component Guidelines | component-guidelines.md | **Filled** |
| Hook Guidelines      | hook-guidelines.md      | To fill    |
```

### 3.3 Spec 应该长什么样

规范应简洁，并以代码为依据。根据主题写出读者实际需要的签名、行为、校验、示例或测试；更宽泛的思考问题和决策提示适合放在 `guides/`。`trellis-spec-bootstrap` 可以协助分析代码并起草或更新文档，完成后仍需对照源码审阅。

#### 3.3.1 Code-Spec vs Guide

| 类型          | 位置                                            | 用途               | 内容形态                                               |
| ------------- | ----------------------------------------------- | ------------------ | ------------------------------------------------------ |
| **Code-Spec** | `<layer>/*.md`（如 `backend/`、`cli/backend/`） | "如何安全地实现"   | 签名、契约、验证矩阵、Good / Base / Bad 用例、必需测试 |
| **Guide**     | `guides/*.md`                                   | "动手前该想到什么" | 思考清单、问题、指向具体 spec 的链接                   |

如果你写的是"别忘了检查 X"——放 guide。如果你写的是"X 接受 `{field: type, …}`，返回 `{…}`，错误矩阵如下，必须覆盖这些测试"——放 code-spec。

#### 3.3.2 选对更新形态

根据要记录的信息选择合适的表达方式。以下是常见形式，可作参考，不要求套用固定模板：

| 你学到了……              | 模板                             | 关键字段                                                      |
| ----------------------- | -------------------------------- | ------------------------------------------------------------- |
| 为什么选方案 X 而不是 Y | **Design Decision**              | Context、Options Considered、Decision、Example、Extensibility |
| 本项目约定 X 这么做     | **Convention**                   | What、Why、Example、Related                                   |
| 一种能复用的解法        | **Pattern**                      | Problem、Solution、Example（Good + Bad）、Why                 |
| 一种会出问题的做法      | **Forbidden Pattern**（`Don't`） | 错误片段、为什么糟、改成什么                                  |
| 容易犯的错              | **Common Mistake**               | Symptom、Cause、Fix、Prevention                               |
| 非直觉的行为            | **Gotcha**                       | `> Warning:` 引用块，说明何时触发、怎么处理                   |

#### 3.3.3 写清关键契约

涉及命令、API、数据结构或跨层行为时，说明相关输入、输出、校验和失败行为。需要时用示例或测试引用解释契约。只写出安全应用规则所需的细节；不要求每份规范采用固定段落数量，也不要求一律列出完整错误矩阵。

#### 3.3.4 对比示例

一条合格的 **Convention**（放在 `backend/database-guidelines.md`）：

````markdown
#### Convention：用 ORM batch 方法，别在循环里一条一条写 DB

**What**：对 N 条数据，调一次 ORM 的 batch 方法（`createMany` / `updateMany` / `deleteMany`）。不要把单行 `create` / `update` / `delete` 套进 `for` 或 `Promise.all`。

**Why**：每次 DB 调用都是一次 round-trip。线上接口里一个 200 条的循环就能把 p99 从 50ms 悄悄拖到 8s——这种坑已经在 code review 里抓到过两次（PR #312、#417）。Batch 方法把 N 次 round-trip 压成一次 SQL，DB 可以自己规划写入。

**Example**：

```ts
// ✅ 正确——一次 round-trip
await prisma.user.createMany({ data: users });

// ❌ 错误——N 次 round-trip
for (const user of users) {
  await prisma.user.create({ data: user });
}

// ❌ 还是错——并发的 N 次 round-trip
await Promise.all(users.map((user) => prisma.user.create({ data: user })));
```

**Batch 不可用时**：把循环包进单事务（`prisma.$transaction`），至少是一个逻辑单元；加注释说明为什么 batch 用不了。

**Related**：`quality-guidelines.md#performance`、`error-handling.md#transactions`。
````

一条**差的 spec**——没签名、没示例、没 why、没测试点：

```markdown
#### Database

- Use good query patterns
- Be careful with SQL
- Follow best practices
```

一条**过度规范**——机械规则、没有原因、扼杀判断：

```markdown
#### Variable Naming

- All boolean variables must start with `is` or `has`
- All arrays must end with `List`
- All functions must be less than 20 lines
- All files must be less than 200 lines
```

底线：具体、可操作、带代码示例、说清 _why_；对 code-spec 而言，还要有足够的签名 / 契约细节让 sub-agent 不用追问就能照做。

### 3.4 Bootstrap 引导首次填充

`trellis init` 会创建一个 bootstrap 任务（`00-bootstrap-guidelines`），用于组织首次项目配置。按实际需要整理初始上下文和规范。需要结合代码进行分析时，可使用 `trellis-spec-bootstrap` 起草相关内容，再对照源码检查；不适用的模板章节可以删除。
