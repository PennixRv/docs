---

从 `0.7.1-beta.9` 起，22 个平台生成的 `trellis-brainstorm` 由 `trellis-request-intake` 替代。`trellis-start` 初始化会话，`trellis-continue` 恢复原生任务，接入入口分流新请求。同一目标的变化返回最早受影响阶段，独立工作单独接入；复用既有授权，保留直接小改的原有边界。

## 探索由业务阶段承接

| 职责                                                                 | 负责阶段           |
| -------------------------------------------------------------------- | ------------------ |
| 核对症状、真实目标、约束、假设和用户确认                             | 目标探索与需求核对 |
| 探索机制与真实候选，适用时包含现状或不做；按证据筛选，证据充分即停止 | 决策空间构造与归并 |
| 解决实质取舍，关联需求、设计及验证，整体审查和完整展示方案，接受结果 | 解决方案设计与收敛 |
| 获得独立实施授权后，按已接受合同实施和验证                           | 任务实施与测试验证 |
| 审查交付、剩余工作、接受条件及资源处置                               | 交付审查与现场收尾 |

不另设发散探索或 idea-to-closed-plan Skill；其有用方法归入对应阶段，避免形成竞争的规划状态。即使同一明确答复同时批准方案和实施，结果接受与实施授权仍是不同的原生记录。

## 支持性 Skill 与协作

`before-dev` 和 `check` 读取实际阶段与合同引用，文件名不能证明授权。`break-loop` 依据证据分析，不使用编造的百分比；`update-spec` 仅记录实际需要的合同并复用已有材料。规范初始化使用已授权工具和索引；工具安装、索引重建及委派写入须符合各自授权边界。

Pennix 决策提问提供用户选择和审查方法，不接管阶段。工作流路由、会话交接、项目更新、资源清理和 Context Mode 保留各组件边界。Teamwork teammate 只提交研究、审查或验证报告，不写产品代码；`general` 是协作模式，batch 必须有已验证 adapter，交互式 `run`／`spawn` 不能冒充 batch。

Extra 集合保留明确调用策略。UI 原型要求有效且仅开发环境启用的 variant，普通或无效 URL 保留现有页面，实验导入和渲染不能进入生产。架构报告按表达需要使用图示；复盘先发现当前宿主实际使用的规则来源。

## 更新与历史

先运行 `trellis update --dry-run` 预览，再运行 `trellis update`。迁移仅删除内容匹配已知生成哈希的旧 Skill；定制内容及无关 Skill 保留并待审查。任务和交接历史保持。历史参数 `trellis mem extract --phase brainstorm|implement|all` 仍按任务创建／开始切分对话，并非五个业务阶段；未知或不适用的 mem 参数明确报错，包括不支持的 `--task`。
