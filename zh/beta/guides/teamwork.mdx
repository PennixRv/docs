---
title: 'Teamwork 角色配置与执行'
description: '配置专业角色、执行候选及与角色正交的协作模式。'
---

从 `0.7.1-beta.14` 起，Teamwork 将项目配置解析为不可变执行计划，并通过前台 provider 进程运行受管 batch。它与 Paseo 的 workspace、worktree 委派机制保持独立。

## 配置与角色卡

| 项目文件                                 | 职责                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `.trellis/agents/teammate-profiles.json` | schema 2：默认 profile、专业角色路径、默认执行候选，以及候选的 provider/model/reasoning effort/options |
| `.trellis/agents/teammate.md`            | 通用报告、证据、源码与 Git 义务                                                                        |
| `.trellis/agents/profiles/*.md`          | 精确的专业角色指令                                                                                     |
| `.trellis/teamwork.json`                 | schema 2：默认模式、各模式成员数与并发上限、共享存活进程预算与预留                                     |

六个 profile 分别是 `architecture`、`review`、`research`、`exploration`、`verification`、`diagnosis`。research 调查外部证据，exploration 探索本地源码主题，diagnosis 从已观察到的故障出发。每个 profile 自带三个可编辑执行候选，均默认选择 `codex-sol`；architecture/review/diagnosis 的备选为 Copilot Sol 与 Opus，其余为 Copilot Sol 与 Sonnet。architecture 默认使用 `xhigh`，其余使用 `high`。上下文长度保持 provider 默认值。

组织委派前先读取项目实际值：

```bash
trellis teamwork config --profile architecture --mode committee
```

profile 与 mode 正交。`general` 允许 1–32 个显式委派项，`advisor` 允许一到三位独立顾问，`committee` 要求两到三个，并使用不同的 `lens` 表达各自关注点。委员会成员共享任务、证据和接受合同，不能读取同伴报告。配置中的默认成员数用于组织委派，构造器不会自动复制委派项。每个候选均需填写 `selection_reason`，说明选择理由，以及其他候选是否有助于本次任务。

从 `0.7.1-beta.19` 起，general/advisor/committee 的默认成员数分别为 1/3/3，并发上限为 8/3/3；共享存活进程预算为 8，非 batch 预留为 0。成员数和同时执行数分别控制计划构造与运行准入；有效并发还受显式请求、共享资源及已验证宿主上限约束。`teamwork config` 与 batch 预检输出解析后的 `capacityPolicy`，它不是另一套配置源。schema 2 忽略旧 YAML 容量键并给出诊断；schema-1 项目迁移前保留旧配置兼容，显式环境覆盖也会显示诊断。YAML 继续管理空闲清理设置。

角色卡是普通 Trellis Markdown，与通用角色卡和模式结果合同共同注入，不注册 provider 原生 persona，也不修改 `AGENTS.md`/`CLAUDE.md`。源码、Git、记忆与递归委派约束属于角色义务。工具权限自动允许，Codex 默认无沙箱、使用 `approvalPolicy: never`；这些角色边界不构成与宿主 AGENTS、Skills 或记忆的技术隔离。

## 构造与执行

准备 schema-2 草稿前，读取当前原生任务及阶段。草稿绑定 `task_id`、`phase_id`、`task_route_revision`、`input_revision`、`plan_summary`、`coordination_mode`、`batch_id`、`session_id`、`deadline` 及显式 `assignments`。每个委派项记录 profile/候选、选择理由、摘要、范围、输入、来源摘要、接受条件和重试预算。内置 `trellis-teamwork` Skill 说明完整草稿格式与报告合同。

```bash
trellis teamwork plan draft.json --task TASK_DIR --output TASK_DIR/plan.json --dry-run
trellis teamwork plan draft.json --task TASK_DIR --output TASK_DIR/plan.json
trellis teamwork batch TASK_DIR/plan.json --task TASK_DIR --preflight
trellis teamwork batch TASK_DIR/plan.json --task TASK_DIR --json
```

构造器先验证 brief 与路径，再写入冻结后的有效配置、角色及能力摘要，并保留既有不可变文件。plan 与 claim 使用 schema 2，新派发使用 schema-2 内容报告；历史冻结派发保留 schema-1 报告合同。旧版自定义 schema-1 profile 文件需要显式转换，转换前会明确拒绝；原生更新会刷新未修改的生成默认值。

## 输入与最终结果

角色规则和模式结果合同在初始化时提供；任务、验收条件、产物身份及参考资料作为独立任务输入。上下文清单的 `delivery` 支持 `inline`（默认内联）、`required`（工作前完整读取）和 `on-demand`（按需读取）。引用附带来源摘要；新 batch 在派发前和完成后核对参考文件内容，但这不能证明模型实际读完了每个字节。

代理调用使用 `run --json`、`batch --json` 或 `wait SESSION --as main --from WORKER --json`。它们返回统一的 `trellis_result` 信封，分开记录执行事实、关联报告、结构校验和运行处置；`semanticValidation: not_run` 表示语义接受仍由主代理负责。默认 run 文本及 wait 事件保留人工与兼容视图。batch 结果附校验后的报告正文、路径及 SHA-256；持续会话 wait 将回复绑定到输入序号与轮次，并保留运行中的 worker。

schema-2 内容报告包含 `schema_version: 2`、`status`、`answer`、非空 `evidence` 及 `limitations`、`unresolved`、`deviations` 数组。交互式回复直接返回该 JSON；受管报告还须原样复制本次派发身份并写入指定路径。provider 的 `done`、模型的 `complete` 或 `ALL_ACCEPTED` 均不代表原生任务已接受。非法或空报告明确失败；历史报告标记为 `legacy`，不推造新版有效回答。

预检不启动 provider，并返回 `processProbe: not_run`。真实执行会核对 provider 公布的模型与思考深度，负责重试、验证报告、确认进程结束，并持久化终态回执。结果为 `ALL_ACCEPTED`、`SETTLED_WITH_FAILURE` 或 `RECONCILIATION_REQUIRED`。任务接受仍由主协调者通过原生阶段操作完成。

已有终态回执会直接返回，不再次派发。不确定的 attempt 需要对账并保留容量，即使协调器已退出也不例外。协调器停止不代表其 provider 进程已停止；未解决的容量保留会阻止会话清理及容量复用，不能通过删除保留文件绕过准入。

## Provider 与验证边界

| Provider                  | 传输                                                      |
| ------------------------- | --------------------------------------------------------- |
| Codex                     | 原生 app-server                                           |
| Claude                    | 原生 stream-json                                          |
| Copilot                   | CLI 的 ACP 接口：`copilot --no-auto-update --acp --stdio` |
| DeepSeek Harness（`dsh`） | ACP：`dsh --profile acp`                                  |

Copilot 支持非交互 CLI，此处选用 ACP 作为结构化传输。ACP v1 只有 user 内容块，因此角色指令与任务数据使用独立的纯文本块，不声称拥有独立的 system 优先级。ACP 在确认一轮完成后保留角色，不在每次追问中重复整份规则；恢复时重新建立规则。Codex 与 ACP 的中断路径会等待旧 turn 的终态响应，再发送替代输入。恢复使用各 provider 公布的能力，包括 DSH 的 `session/resume`。标记为 `adapter-contract` 的能力快照来自静态代码合同，不代表真实后端探测已成功。

本次 Linux 验证已运行真实 Codex/Copilot 单次调用和包含两个委派项的受管 batch，两份报告均被接受，重试次数均为零。Claude 与 DSH 有协议夹具验证，本次未连接真实账户。`run`、`spawn` 仍用于交互式会话，不能替代受管 batch 执行。
