---

Trellis 是 **Team-level Agent Harness with built-in LLM wiki**。

落到实现上，它是两套系统共用同一批项目文件：

- **Agent Harness**：workflow state、hook、skill、sub-agent 和平台适配层，用来约束 AI coding 工作怎么推进。
- **Built-in LLM wiki**：spec、task、research、journal 存在仓库里，让 AI session 从文件重新加载项目知识。
- **Team-level layer**：workflow、spec、task 走 git 跟踪，workspace memory 按 developer 隔离，让多人和多 AI 工具使用同一套约定。

本文档把这个定位映射到当前 Trellis 的 feature、实现这些 feature 的模块，以及本地定制时应该检查哪些文件。使用流程见 [How It Works](/zh/start/how-it-works)。

> Trellis 采用 AGPL-3.0 协议。团队内部使用不需要额外授权；基于 Trellis 衍生产品或服务做商业化，需要提前联系：**klein@mindfold.ai**。

## 设计理念

Trellis 把 AI coding 当成工作流和知识管理问题，而不是一次聊天。

| 理念               | 实现规则                                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 显式记录工作流状态 | Task `status` 和 `[workflow-state:STATUS]` block 告诉主会话当前在哪个阶段。                                                                  |
| 把持久知识放进文件 | 需求、spec、research、journal 存在 `.trellis/` 下，不只存在对话历史里。                                                                      |
| 按职责拆分工作     | 调研、实现、验收分别走不同 agent 或 skill，取决于平台能力。                                                                                  |
| 控制上下文范围     | JSONL 只列当前任务需要的 spec/research 文件，不把整个仓库塞进上下文。                                                                        |
| 保留审查边界       | 按已接受且已授权的合同实施；收尾操作改变任务生命周期，`/trellis:finish-work` 记录会话进度。                                                  |
| 支持团队和多工具   | 同一套 `.trellis/` 模型适配 Claude Code、Cursor、Codex、OpenCode、Kiro、Gemini、Qoder、Copilot、Droid、Pi、Kilo、Antigravity、Devin 等工具。 |

## Feature 全景

### Agent Harness

| Feature                           | 作用                                                                   |
| --------------------------------- | ---------------------------------------------------------------------- |
| 路由式任务工作流                  | 在 `.trellis/workflow.md` 和阶段 Skill 中选择有序业务阶段路线。        |
| 每轮 workflow-state breadcrumb    | 在支持 hook 的平台上，把当前 next-action 规则注入主会话。              |
| 任务与阶段状态                    | 在 `.trellis/tasks/<task>/` 中保存生命周期、阶段路线、证据和任务产物。 |
| Research / implement / check 角色 | 分开调研、写代码、验收。                                               |
| Read-before-write                 | 让 implement/check 路径在改文件前读取 PRD 和相关 spec。                |
| 交付收尾边界                      | 审查交付和剩余工作；任务完成与会话日志是独立操作。                     |

### Built-in LLM wiki

| Feature                 | 存什么                                                                       |
| ----------------------- | ---------------------------------------------------------------------------- |
| Spec library            | `.trellis/spec/` 下的项目约定和 thinking guide。                             |
| Task knowledge          | `.trellis/tasks/` 下的 PRD、技术设计、实施计划、research 和 JSONL manifest。 |
| Workspace memory        | `.trellis/workspace/<developer>/` 下的开发者 journal。                       |
| Workflow documentation  | `.trellis/workflow.md` 里的可执行工作流契约。                                |
| Local customization map | 内置 `trellis-meta` references，说明每类行为由哪些生成文件负责。             |

### Team-level behavior

| Feature                              | 支持什么                                                          |
| ------------------------------------ | ----------------------------------------------------------------- |
| Git-tracked workflow/spec/task files | 新成员 clone 仓库后拿到同一套工作流和约定。                       |
| Per-session active task pointer      | 多个窗口可以在同一仓库里做不同任务。                              |
| Subtask tree                         | 父任务和子任务分别保留任务记录，并各自选择阶段路线。              |
| Cross-platform adapters              | 团队可以用不同 AI 工具，同时共享同一套 `.trellis/` 事实源。       |
| Spec distillation                    | 一个任务里的稳定经验可以提升到 `.trellis/spec/`，供未来任务复用。 |

## Workflow module

`.trellis/workflow.md` 按任务所选路线，将工作路由到相应业务阶段和协作组件。Trellis CLI 将阶段路线及阶段记录保存在 `task.json` 的 `meta.task_workflow` 中。

各业务阶段有各自的目标和转换条件：

- 目标探索与需求核对阶段
- 决策空间构造与归并阶段
- 解决方案设计与收敛阶段
- 任务实施与测试验证阶段
- 交付审查与现场收尾阶段

每个阶段 Skill 维护该阶段的流程和图示。证据表明某些阶段不会带来价值时，任务路线可以省略这些阶段。路线离开目标探索与需求核对阶段前，必须保留经用户确认的需求基线。开始实施前必须接受实施合同并另行取得授权。交付审查与现场收尾阶段审查结果，并决定完成、取消或返回受影响的前序阶段。

工作流文档也会按需路由平台 Skill 和组件 Skill。Trellis Teamwork 与 Paseo 可以提供协作能力，任务和阶段状态仍由 Trellis CLI 管理。

## Workflow-state module

在支持 hook 的平台上，`inject-workflow-state.py` 或等价 plugin 会在每条用户 prompt 时运行。

运行时契约是：

1. 解析 Trellis 根目录和当前会话的活动任务。
2. 读取任务生命周期状态和所选阶段路线。
3. 解析 `.trellis/workflow.md` 中适用的 `[workflow-state:...]` 区块。
4. 将匹配的工作流指引注入宿主上下文。

标记格式：

```text
[workflow-state:planning]
...
[/workflow-state:planning]
```

Hook 脚本只负责解析，不保存 breadcrumb 文案副本。缺少匹配 block 时，hook 输出 `Refer to workflow.md for current step.`

任务状态表示生命周期，不表示当前业务阶段。当前阶段由 `meta.task_workflow.current_phase_id` 记录；运行 `task.py phase show <task>` 可以查看所选路线。工作流状态区块用于提供上下文指引，不是第二套状态来源。

`no_task`、`planning` 和 `in_progress` 区块提供较高层级的生命周期指引。`task.py create` 可以设置当前会话的活动任务指针；只有路线和授权条件满足时，`task.py start` 才会进入实施。接受收尾结果后，`task.py complete` 完成任务并保留其目录。[Beta 任务目录治理](/zh/beta/guides/task-layout)新增按状态自动移动。

## Task store module

每个任务是一个目录：

```text
.trellis/tasks/<MM-DD-slug>/
├── task.json
├── prd.md
├── design.md
├── implement.md
├── implement.jsonl
├── check.jsonl
└── research/
```

关键文件：

| 文件              | 作用                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| `task.json`       | 生命周期状态、`meta.task_workflow` 下的阶段路线与阶段记录、负责人、分支、任务关系和扩展元数据。 |
| `prd.md`          | 需求、约束、验收标准和 out-of-scope。                                                           |
| `design.md`       | 复杂任务的技术设计：边界、contract、数据流、兼容性、取舍。                                      |
| `implement.md`    | 复杂任务的执行计划：有序 checklist、验证命令、review gate、回滚点。                             |
| `implement.jsonl` | 实现上下文使用的 spec / research manifest。                                                     |
| `check.jsonl`     | Review 和验证上下文使用的 spec / research manifest。                                            |
| `research/`       | 只读调研或规划流程写入的调研产物。                                                              |

Task lifecycle hook 是命令事件，不是通用 status watcher：

| Lifecycle event | 触发时机                              | 含义                                                        |
| --------------- | ------------------------------------- | ----------------------------------------------------------- |
| `after_create`  | `task.py create` 结束                 | 任务目录已经存在。                                          |
| `after_start`   | `task.py start` 结束                  | 当前会话将该任务设为活动任务。                              |
| `after_finish`  | `task.py finish` 清掉 session pointer | 当前 AI session 脱离该任务；任务可能还在其他 session 继续。 |

## Active-task runtime module

Current task 按 session 隔离：

```text
.trellis/.runtime/sessions/<session-key>.json
```

这个文件把一个 AI session 或窗口指向一个任务。同一仓库里的不同窗口可以做不同任务。

`.trellis/.current-task` 是命令行场景的 fallback。平台能提供 session identity 时，session runtime pointer 优先。

## Context-loading module

Trellis 通过三条路径加载上下文：

| 上下文类型                   | 来源                                                                                    | 使用者                            |
| ---------------------------- | --------------------------------------------------------------------------------------- | --------------------------------- |
| 启动上下文                   | `.trellis/scripts/get_context.py`                                                       | 主会话启动报告。                  |
| 每轮 workflow state          | `.trellis/workflow.md` blocks                                                           | 主会话 next-action 指引。         |
| Task artifact / spec context | `prd.md`、`design.md`、`implement.md`、`implement.jsonl`、`check.jsonl`、research files | 主会话 Skill 和明确授权的工作包。 |

JSONL 行是普通文件引用：

```text
{"file": ".trellis/spec/docs-site/docs/style-guide.md", "reason": "Docs writing style"}
```

标准流程里，task artifact 和 JSONL manifest 分开读取。统一顺序是
`jsonl entries -> prd.md -> design.md if present -> implement.md if present`。
`implement.jsonl` 和 `check.jsonl` 列 spec 和 research 文件。没有 `file` 字段的
seed row 会被 reader 跳过。源文件由实现和 review 时按需读取，不预先登记在
JSONL 里。

## Platform adapter module

平台适配只提供主会话上下文、阶段提示、shell 身份和 Skills/commands。主会话负责计划、授权与接受；协作通过 `trellis teamwork` 的只读 teammates 或实施阶段的 `paseo-based-parallelism` delegated-agent。角色位于 `.trellis/agents/`，Kiro 另保留主入口。普通 check Skill 和可选上下文清单不构成子代理路由。

## LLM wiki modules

Wiki 侧是一组 AI session 可以反复读取的仓库文件。

| Module                 | 路径                              | 内容                                           |
| ---------------------- | --------------------------------- | ---------------------------------------------- |
| Spec library           | `.trellis/spec/`                  | 团队约定、package/layer 规则、thinking guide。 |
| Task knowledge         | `.trellis/tasks/`                 | 需求、设计、实施计划、调研和上下文清单。       |
| Workspace memory       | `.trellis/workspace/<developer>/` | 开发者 journal 和索引。                        |
| Workflow reference     | `.trellis/workflow.md`            | 工作流契约和 next-action prompt blocks。       |
| Trellis meta reference | 内置 `trellis-meta` skill         | 生成文件的本地架构和定制地图。                 |

稳定团队规则放 `.trellis/spec/`。任务事实放任务目录。Session notes 放 `.trellis/workspace/<developer>/`。

## Finish module

交付审查与现场收尾阶段将当前交付与已接受的任务结果对照，解决实质缺口或记录剩余工作，并接受完成或取消处置。接受收尾结果后，`task.py complete` 将任务标记为完成。四个生命周期状态与五个业务阶段相互独立；按状态自动移动目录见 [Beta 任务目录治理](/zh/beta/guides/task-layout)。

`/trellis:finish-work` 在工作区日志中记录会话进度，不会完成或归档任务。会话日志和正式会话交接都独立于任务阶段路线及生命周期。

## 生成文件和受保护文件

`trellis init` 和 `trellis update` 会生成本地文件，但本地改动本身很重要：

| 路径                             | 判断规则                                                                   |
| -------------------------------- | -------------------------------------------------------------------------- |
| `.trellis/workflow.md`           | 项目工作流事实源；需要有意识地改。                                         |
| `.trellis/spec/`                 | 团队拥有；模板更新不会覆盖 package / layer spec。                          |
| `.trellis/tasks/`                | 工作历史；避免手动删除 active task。                                       |
| 平台目录                         | 工具适配层；改行为前先看本地 settings。                                    |
| `.trellis/.template-hashes.json` | owner 写入的模板基线；核查漂移并走原生更新或修复入口，不手改哈希掩盖定制。 |
| `.trellis/.runtime/`             | Runtime 状态；通常不手改。                                                 |

做本地定制时，用内置 `trellis-meta` skill 当地图。它会要求 AI 先读本地架构 references，检查项目实际文件，再修改项目副本，而不是去改 `node_modules` 或全局安装目录。

[Beta 资产维护指南](/zh/beta/guides/asset-maintenance)说明 `0.7.1-beta.9` 新增的快照、恢复、清理及共享维护锁。

## 定制入口

| 目标                                           | 先看哪个文件                                                                                 |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 改 phase 顺序、required step、next-action 文案 | `.trellis/workflow.md`                                                                       |
| 改任务创建、状态和阶段路线                     | `task_store.py`、`task_workflow.py`、`task.py`                                               |
| 改 spec 加载或 JSONL 规则                      | `.trellis/workflow.md`、`.trellis/scripts/common/task_context.py`、平台 agent / prelude 文件 |
| 改 hook 行为                                   | 平台 hook settings 加 `.trellis/scripts/` 下的 hook 实现                                     |
| 改 implement / check agent 行为                | 平台 agent 文件和任务 JSONL 上下文规则                                                       |
| 增加团队自己的编码规则                         | `.trellis/spec/` 或项目本地 skill                                                            |
