Trellis Teamwork is the user-facing collaboration interface for bounded teammate processes and durable discussions. Its CLI is `trellis teamwork`; it uses Trellis Core's Channel event and storage model underneath.

Choose the simplest route that fits the work:

| Need                                                      | Teamwork route    |
| --------------------------------------------------------- | ----------------- |
| One bounded question, research task, or review            | `teamwork run`    |
| Independent work units with one shared completion receipt | `teamwork batch`  |
| A durable topic with comments, status, and summary        | Forum and threads |

Teammates use one generic role contract for investigation, research, review, verification, and assigned report writing. They do not implement product code or start nested agents. A fixed batch is submitted as one plan; after submission, the program owns dispatch, waiting, retry decisions, artifact checks, and the terminal receipt.

## Run one bounded assignment

Use `teamwork run` when one teammate can return a self-contained answer. Include the question, evidence boundary, and expected report in the prompt:

```bash
trellis teamwork run design-review \
  --provider codex \
  --message 'Review the design for failure cases. Cite repository paths and do not edit product source.' \
  --timeout 10m
```

On success, the command prints the final answer and removes its ephemeral session. On failure, it keeps the session for inspection. Use `trellis teamwork list`, `trellis teamwork messages <name>`, and `trellis teamwork kill <name> --as <teammate>` to inspect or stop a process when needed.

## Submit a fixed batch

Use a batch for independent work units whose objectives, read scope, report destinations, acceptance criteria, teammate profiles, and per-unit retry limits can all be frozen before dispatch. Submit the complete plan once:

```bash
trellis teamwork batch .trellis/tasks/<task-id>/teammates/<batch-id>/plan.json
```

After submission, wait for the program's terminal receipt. Do not inspect partial reports, dispatch replacements, select retries, or route follow-up messages while the batch is active. The program refills released capacity from the FIFO queue and settles each work unit under its own retry limit. A timeout continues the same attempt; a confirmed execution or acceptance failure may create a new attempt within that unit's limit. An unknown outcome requires reconciliation rather than a duplicate dispatch.

No teammate host adapter has passed the capability gate in this build. The batch command therefore fails closed before writing coordination state. Do not reproduce a blocked batch with manual per-teammate commands. Provider contracts and a configured CLI alone do not establish that a host has passed the required capability gate.

After a terminal business receipt, review accepted reports against the owning Trellis task, resolve any terminal failures there, and continue its normal implementation, testing, review, and status lifecycle.

## Independent evaluation

An advisor is one ordinary work unit with an evidence-backed recommendation. A committee is exactly two independent evaluations of the same frozen question and acceptance contract, with distinct lenses and non-overlapping evidence. The teammates do not exchange findings or revise their reports in response to one another. Compare reports only after the whole batch has a terminal receipt; a failed member makes the evaluation incomplete.

## Keep a durable discussion

Create a forum when a topic needs a persistent thread history:

```bash
trellis teamwork create design-feedback \
  --type forum \
  --description 'Design feedback and follow-up decisions.' \
  --by main

trellis teamwork post design-feedback opened \
  --as main \
  --thread error-recovery \
  --title 'Error recovery behavior' \
  --description 'Track evidence and decisions for recovery behavior.' \
  --text 'Add one thread per review topic.'

trellis teamwork forum design-feedback
trellis teamwork thread design-feedback error-recovery
```

Use `teamwork post` to add comments, status, or a summary. Use the forum and thread commands to read their reduced state; they account for thread lifecycle events.

## Command reference

The main commands are `create`, `run`, `batch`, `spawn`, `send`, `wait`, `messages`, `interrupt`, `kill`, `forum`, `thread`, `post`, `context`, and `prune`. Run `trellis teamwork --help` or `trellis teamwork <command> --help` for the installed CLI's complete options.

The public command and bundled Skill use the Teamwork name. “Channel” remains the name of the underlying Core collaboration model and its persisted event contract.
